# Choosing a CI Test Framework for Claude Code Agent Skills

## Bottom line first

Neither `cc-plugin-eval` nor `waza` cleanly fits your full use case as it stands today, but they fail in very different ways, and the answer is not a coin flip.

`cc-plugin-eval` is the right starting point. It is the only one of the two that was actually built for Claude Code — it embeds the Claude Agent SDK, loads your plugin via `plugins: [{ type: "local", path }]`, and captures tool calls through real SDK `PreToolUse` hooks. `waza` evaluates GitHub Copilot CLI through `github.com/github/copilot-sdk/go`, with the Copilot binary bundled into the Go executable via git-LFS-tracked `internal/embedded/zcopilot_*.zst` blobs. Adopting waza for a Claude Code skill suite would mean implementing a new `AgentEngine` from scratch and tracking a pre-1.0 Go codebase that is still renaming its own core types in flight (the `TestRunner→EvalRunner`, `BenchmarkSpec→EvalSpec` rename landed three weeks ago). That is the wrong adapter to start with.

But `cc-plugin-eval` will not get you to a working PR-review test on its own either. It has no GitHub fixture layer, no user-defined content assertions, no declarative way to write a hand-crafted "this PR has a SQL injection, the review must flag line 42" test case, no published GitHub Action, and a bus factor of one (the visible git history is essentially Dependabot churn against work by a single human maintainer). It is well-engineered for one specific question — "did the right plugin component trigger?" — and structurally not built for the rest.

The recommendation is to adopt `cc-plugin-eval` for the trigger-detection layer that covers your simple, self-contained skills, and to build a thin custom harness on top of the same Claude Agent SDK to handle the PR-review skill. Do not try to combine `cc-plugin-eval` and `waza`; they do not compose, because waza never runs Claude Code in the first place.

## How each framework actually works

`cc-plugin-eval` is a TypeScript ESM CLI on Node ≥20 that runs a fixed four-stage pipeline against your plugin: `runAnalysis` reads the plugin manifest and frontmatter, `runGeneration` uses an LLM to *synthesise* test prompts (paraphrases, edge cases, negative cases, semantic variations) from the descriptions of your skills and agents, `runExecution` fires those prompts at the real Anthropic API through `@anthropic-ai/claude-agent-sdk` with hook-based tool capture, and `runEvaluation` checks whether the expected `Skill`/`Task`/`SlashCommand` tool name appeared in the captured stream, optionally followed by an LLM judge that returns a fixed `{quality_score, response_relevance, trigger_accuracy, issues, highlights}` schema. The judge prompt is hard-coded in `src/stages/4-evaluation/llm-judge.ts` and the response is locked to that shape by `JudgeResponseSchema` in `src/types/evaluation.ts`. There is no user-supplied rubric, no `defineScorer` API, no plugin registration mechanism — extending the judge dimensions means forking and editing the schema, the prompt, the aggregation pipeline, and the type system.

`waza` is a single static Go binary (module `github.com/microsoft/waza`, `go 1.26`) with a fat CLI surface — 18 top-level commands across roughly 17,000 LOC under `cmd/waza/` — wrapping a much cleaner business-logic layer under `internal/`. Its execution interface, `AgentEngine`, has two implementations: a `MockEngine` that echoes prompt and file content for deterministic keyword tests, and a `CopilotEngine` that spawns Copilot sessions and listens for `copilot.SessionEvent`s. Tests are declared in YAML (`eval.yaml` at the top level, per-task YAML under `tasks/`) and validated against checked-in JSON Schemas (`schemas/eval.schema.json`, `schemas/task.schema.json`). Critically, waza ships thirteen grader kinds out of the box — `code`, `text`, `file`, `diff`, `json_schema`, `program`, `behavior`, `action_sequence`, `tool_calls`, `tool_constraint`, `skill_invocation`, `trigger`, and `prompt` (the LLM-as-judge one, which spawns a fresh Copilot session and gives the judge model two tools, `set_waza_grade_pass` and `set_waza_grade_fail`, to vote with). For the question "did the skill call exactly these tools, in this order, with arguments matching this regex," waza is dramatically better-equipped than `cc-plugin-eval`. For the question "was the response correct, according to my rubric," waza is also better-equipped — but only if you accept that the model under test is reaching Claude through Copilot's gateway rather than through Claude Code's own runtime.

## How each handles your CI requirements

GitHub Actions integration in `cc-plugin-eval` is essentially absent. The repo's own `.github/workflows/ci.yml` is a standard Node CI for self-testing; there is no `action.yml`, no PR-annotation logic, no published reusable workflow, and `docs/ci-cd.md` is a 22-line file that documents only the framework's own CI. The output formats include JUnit XML, TAP, JSON, and YAML, which means you can pick those up with a generic test-reporter action — but you are writing that workflow yourself. Waza, by contrast, ships a reusable workflow at `.github/workflows/waza-eval.yml` with `workflow_call` inputs, a complete template at `.github/workflows/skills-ci-example.yml`, matrix examples under `examples/ci/`, JUnit XML via `--reporter junit:`, and a `--format github-comment` flag that produces ready-to-pipe markdown for `gh pr comment`. Waza's CI story is materially more polished, and it is the only meaningful axis on which it beats `cc-plugin-eval` for your stated requirements.

Neither framework has any built-in GitHub API mocking. `cc-plugin-eval` has no fixture system for PR diffs, comments, or file lists; its `tests/fixtures/sample-transcripts/` files exist only to test the framework itself. Waza's `inputs.files[]` mechanism lets you copy arbitrary files into a workspace, but those are workspace files, not PR metadata, and the `mcp_servers:` config block passes MCP server configs straight through to the agent runtime, which is the only realistic mocking seam either framework offers. In both cases you would stand up a fake GitHub MCP server yourself, or shim the `gh` binary on `PATH`, or run against a disposable real test repository. Waza's `before_task` hooks make it slightly easier to launch the mock server per-task; `cc-plugin-eval` has no equivalent and would force you to manage that lifecycle from a wrapping shell or TypeScript harness.

Tool-call validation is where the two frameworks diverge most sharply. `cc-plugin-eval` captures `{name, input, toolUseId, timestamp}` for every tool call through `createToolCaptureCollector()` in `src/stages/3-execution/hook-capture.ts`, but its detection layer only asserts on tool *names* and on the component name extracted from inputs (e.g. which sub-skill `Skill` was invoked with). The arguments are in the saved transcripts but the framework will not assert on them. Waza, by comparison, has `tool_constraint` graders with `command_pattern`, `path_pattern`, and `skill_pattern` regexes, plus an `action_sequence` grader with `exact_match`/`in_order_match`/`any_order_match` modes, plus a `tool_calls` grader with required-tool sets and call-count bounds, plus a `behavior` grader with `max_tool_calls`, `required_tools`, and `forbidden_tools` aggregates. If your PR-review skill must demonstrably call `mcp__github__add_comment_to_pending_review` exactly once with a body matching `/injection/i` on a specific `path` and `line`, waza expresses that natively in YAML and `cc-plugin-eval` expresses it as code you have to write yourself against the saved JSON transcripts. This is the single biggest *feature* gap in `cc-plugin-eval` for your use case — and it would be a clean win for waza if waza ran Claude Code.

Cost and token tracking is a strength of both. `cc-plugin-eval`'s `EvalMetrics` reports per-stage costs (generation, execution, evaluation, plugin-load), cache read/creation tokens, hit rate, and savings, with a hard `max_budget_usd` ceiling and an `--estimate`/`--dry-run` projection mode. Anthropic batch API support drops Stage 4 cost by roughly 50% once you cross 50 scenarios. Waza captures `InputTokens`, `OutputTokens`, `CacheReadTokens`, `CacheWriteTokens`, `PremiumRequests`, and per-model breakdown through `SessionUsageCollector`, plus an entire `internal/tokens/` subsystem for measuring SKILL.md token footprint with `waza tokens compare/profile/suggest`. Waza has no `--max-cost-usd` circuit breaker, only observational reporting; `cc-plugin-eval` has the harder budget gate.

Regression detection is partial in both. `cc-plugin-eval` offers `--fast`/`--failed-run <id>` to re-run only previously failed scenarios, `--reps N` for flakiness detection (`consistency_rate`, `flaky_scenarios[]`), and `--samples N` for judge variance — but no cross-run baseline comparison. Waza has a dedicated `waza compare` command that takes two result files and produces per-task score deltas and pass-rate diffs, plus a baseline mode that runs each task twice (with and without the skill enabled) and produces an `ImprovementBreakdown` of quality/token/turn/time deltas. Waza wins on regression tooling.

## Configuration-driven test definition

You asked for YAML-driven tests. This is where `cc-plugin-eval` reveals a deep architectural mismatch with your requirements. You cannot author a single test case in YAML in `cc-plugin-eval`. The 668-line `config.yaml` configures how the framework generates and grades scenarios in bulk — diversity, number of scenarios per component, scope filters, model choices — but every actual test prompt is emitted by an LLM from your plugin's frontmatter. There is no `tests:` array, no place to write `prompt: "review PR #123" / expect_tool_called: ... / expect_body_contains: "SQL injection"`. You can supply a hand-crafted `TestScenario[]` array directly to `runExecution()` from TypeScript, bypassing Stage 2 entirely, and that is the right escape hatch for your PR-review use case — but it is not documented as a supported pattern, and you are writing TypeScript, not YAML.

Waza, in contrast, is YAML-native. Tasks are individual `tasks/*.yaml` files with `inputs.prompt`, `inputs.context`, `inputs.files[]`, `expected.output_contains`, `expected.behavior.max_tool_calls`, and per-task `graders[]`. `tasks_from: file.csv` lets you parameterise. JSON Schema validation is enforced (`additionalProperties: false`). For declarative-CI use, waza's config model is what you would naturally want.

## Code quality and maintenance health

`cc-plugin-eval` is high-quality code with a bus factor of one. The TypeScript config is maximally strict — `strict`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noImplicitOverride`, `noPropertyAccessFromIndexSignature` all on. There are 66 test files across unit/integration/e2e for 104 source files, with Vitest coverage thresholds enforced at 78% lines, 75% functions, 65% branches. The pre-commit and CI pipeline include typecheck, lint (typescript-eslint, sonarjs, import, vitest plugins), format check, knip dead-code, jscpd duplication, madge cycles, Codecov. The package.json author is a single human (`Steve Nims <sjnims@gmail.com>`), the entire visible 50-commit window of development is Dependabot maintenance from 2026-03-23 to 2026-05-11 with no feature commits, the CHANGELOG references feature work via PR numbers but those PRs are not in the visible local history, the project is at 0.4.0, and the README sign-off thanks Monster Energy and deadmau5 — every signal points to a thoughtful solo passion project. Reasonable to depend on; not reasonable to depend on without a fork-and-own contingency plan.

Waza is a real Microsoft project at v0.31.0 with five active contributors, 162 `*_test.go` files, race-enabled test runs in `make test`, golangci-lint, required CI checks on `main`, and roughly fifty commits in a three-week window — very active development. The maturity caveats are real: `IMPLEMENTATION.md` still describes a Python implementation that no longer exists, `AGENTS.md` references a `waza-go/` subdirectory that has been collapsed, core types were renamed within the last three weeks with deprecated aliases littering `spec.go`, and `DEMO-SCRIPT.md` is 18KB of presentation patter that doesn't match the current CLI flags. You would be tracking a pre-1.0 moving target. Documentation surface is bigger but less curated.

## What you would build either way

Whatever framework you pick, the PR-review use case requires custom code that neither framework supplies. You will write a fake GitHub MCP server (or stub `gh` binary, or disposable test repository) to feed deterministic PR fixtures into the skill under test. You will write your own content-assertion layer for review-comment quality, because `cc-plugin-eval`'s fixed quality-score rubric is too coarse and waza's `prompt` grader runs through Copilot. You will write the GitHub Actions workflow that runs the eval, parses results, and posts the PR comment (waza gives you a head start here; `cc-plugin-eval` does not). And you will own a small TypeScript harness that drives the underlying execution.

## Recommended path

Adopt `cc-plugin-eval` for the trigger-detection slice of your CI suite — the simple, self-contained skills where the question is "does the right skill activate when I prompt with X, and not activate for Y." That is exactly what `cc-plugin-eval` was built for and it is the right tool. Configure it through `config.yaml`, run it via JUnit XML output, and write a small GitHub Actions workflow yourself.

For the PR-review skill, build a thin TypeScript test harness on top of `@anthropic-ai/claude-agent-sdk` directly — the same dependency `cc-plugin-eval` uses — driven by your own YAML test definitions. Each YAML test specifies a prompt, a fixture set (PR diff, existing comments, file list), an MCP server config pointing at a local fake GitHub server you launch in a `beforeAll`, and a list of assertions (tool called with arguments matching regex, output contains string, output evaluated by LLM judge with this rubric). Use `cc-plugin-eval`'s `createToolCaptureCollector` pattern verbatim — it is well-designed and worth borrowing rather than reinventing. Use vitest as the runner so you inherit GitHub Actions integration, parallelism, and JUnit output for free. Borrow `cc-plugin-eval`'s `disallowed_tools` and `--rewind` patterns for sandboxing. The implementation effort is modest — perhaps two engineer-weeks for a working PoC covering one PR-review skill against half a dozen fixture PRs, most of which goes into the fake GitHub MCP server.

Do not adopt waza. Adapting it to run Claude Code would require implementing a new `AgentEngine` against the Anthropic SDK, recompiling the Go binary, and tracking a project that is still renaming its public types. The thirteen grader kinds and the YAML-native config are genuinely better than `cc-plugin-eval`'s equivalents, but not enough better to overcome the Copilot-binding and the implementation cost. If, six months from now, waza grows a pluggable engine architecture or a Claude-Code-specific adapter, the calculus changes; until then, it is the wrong fit.

If you would rather not own a custom harness at all, the realistic third option is to wait — neither framework is mature enough to be load-bearing for production Claude Code skill CI today, and the space is moving quickly enough that a six-month patience window may well surface a better-fitting tool. But assuming you need something in CI now, the cc-plugin-eval-plus-custom-harness path is the lowest-effort way to get there with the fewest sunk costs if you have to rip and replace later.
